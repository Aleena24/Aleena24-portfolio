3.1

The problem & the system

College operations traditionally live in disconnected tools — admission registers, spreadsheets for allocation, paper attendance, separate portals for every department. Data gets re-entered, drifts out of sync, and nobody can see a student's full journey.

CelerSCET replaces that with one interconnected platform: every stage of the student lifecycle flows into the next, every write is attributable, and every module shares the same identity, permission and notification systems.

What the platform runs
  • Admissions — enquiry to admitted, across quotas and degree types
  • Provisioning — applicant → student, batches, classes, SR numbers, email
  • Academics — timetables, attendance, assessment, course plans, curriculum
  • Administration — user & role management, approvals, audit, payments
  • Campus life — calendar & events, leave, library, placement, forums, HDP
My contribution
  • Bootstrapped the monorepo and overall architecture (Jan 2026, solo start)
  • Built admissions, payments, provisioning, calendar & events, dashboards, data supervision
  • Own auth/sessions, notifications & approvals engines, cloud infrastructure
  • Integrator for the team — 680+ PRs reviewed & merged; top author of the test suite

Architecture

3.4

Engineering challenges

The hard parts of an ERP aren't screens — they're correctness, integrity and operations. A few problems this system forced me to solve properly:

Correctness

Reports that account for every row

Admission reports silently lost applicants: offset pagination over non-unique sort keys, status sets that drifted from the real state machine, filters built on free text instead of foreign keys. I rebuilt them around single sources of truth — one status grouping, one facet rule, stable id-tiebroken paging — with live counts so a filter that drops rows can never look "correct".

Workflow design

Provisioning as a dependency chain

Turning 500+ admitted applicants into students touches batches, class allocation, section splits, SR number generation and institutional email. I built it as a guided multi-step pipeline that follows the real dependency order, generates identifiers deterministically, and notifies each student when their account goes live.

Authorization

Access control shaped like a real institution

A three-layer permission engine (role defaults → designation extensions → admin overrides) plus relational rights — HoD, class teacher, coordinators — because real authority is scoped, not global. Sessions enforce device limits with revocation that actually works: per-request checks, realtime kill, and a heartbeat fallback.

Data integrity

Single sources of truth, enforced by tests

Every cross-cutting rule — date validation bounds, vocabularies, status groups — lives in exactly one module, mirrored client and server. The 275-file test suite includes guards that fail the build if a second copy of a rule ever appears. Drift becomes a red test, not a production bug.

Operations

Deploys that don't lie

I own the pipeline: Cloud Build triggers building staging (dev) and production (main) onto Cloud Run. Solved the classics properly — stale frontends fixed with a real cache policy (hashed assets immutable, index.html no-cache), build times cut from 45+ minutes back to ~4 by removing a runaway image-pull step, env flags made observable at boot.

Accountability

Auditability as a first-class feature

Every database write is attributable to a user; deleted rows keep before-images and can be restored; the audit schema is reachable only through guarded RPCs; nightly pg_dump backups land in Cloud Storage. In an institution, "who changed this?" must always have an answer.
